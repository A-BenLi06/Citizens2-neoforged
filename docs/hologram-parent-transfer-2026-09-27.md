# Holograms following a parent across dimensions

## Reproduced gap

The mounted-tree follow-up moved actual passenger trees, but several hologram renderers follow their parent without riding it. Their coordinate-only helper called `Entity.teleportTo(x, y, z)`, which kept the helper in its old dimension. HologramTrait noticed the parent's world change once, then stopped updating a stationary parent even though its live helper had never arrived. The retained negative runtime run fails at `outbound_0_dimension_0` with a text display still in the source level.

## Native movement and retry

SingleEntityHologramRenderer now synchronizes a mismatched helper through its owning NPC's teleport lifecycle before rendering its local offset. It retains helper NPCs and their settings, reads their current native entities after transfer and moves item anchors with their passenger through the existing tree coordinator. Cloud and text-display admission positions use their actual renderer offsets. Mounted name/text/interaction/item-display helpers continue using the parent tree path. Native world/virtual ownership and tracking remain authoritative.

A renderer with a helper in another dimension remains eligible for updates even when the parent is stationary. Canceled teleport events, rejected native admission and denied item dismounts leave the source entities and positions intact and retry on later ticks. Hologram visibility follows the parent's dimension, so a pending helper cannot remain visible in the old world. This dimension rule applies to hologram helpers, not every ordinary ClickRedirect NPC.

## Callback ownership and cleanup

The render frame validates the parent entity/location and helper lifecycle around callbacks. Reentrant rendering of the same renderer is suppressed. Parent transfer/removal, line clearing/replacement and a newer helper teleport cannot be overwritten by the older frame. Native mounts use the existing guarded riding operations.

Renderer destruction detaches its owned reference before dispatching NPC removal. Item anchors and item NPCs are retired through captured references. Clearing detaches the old line list before callbacks, and reset captures its old renderers and name line before cleanup. A removal listener can therefore add a replacement without the old cleanup deleting it. Removed/despawned traits suspend rendering; stale references cannot respawn helpers. A subsequent legitimate spawn reactivates the attached trait.

## Validation

The dedicated fixture passes **822 checks** on NeoForge **21.1.248**, with the project default still **21.1.233**. Its matrix covers ordinary/virtual parent NPCs and ordinary/virtual helpers across all built-in text, cloud, armor-stand, mounted interaction/display, item-anchor/item and name renderers. Both worlds contain natively admitted synthetic player sessions with real protocol encoding and packet observation.

Checks cover round trips, stable helper NPC identity/UUIDs, native level indexes, exact relative positions, old-entity removal packets, new-world pairing, individual personalized text payloads, passenger relationships/order, group cleanup, canceled/rejected transfer retries, denied item detachment, hidden pending helpers and eventual arrival. Callback cases exercise parent destruction, trait removal, clearing, replacement, reentry, newer parent/helper teleports, native join-time replacement and a new line created by a removal listener. The final run also checks that a removed trait cannot recreate its helpers through an old reference.

The initial 553-check and expanded 819-check successful runs are retained separately; they are not the final gate. Reproduction is documented in [the audit README](../tools/hologram-transfer-runtime-audit/README.md). Final regression/build results and source/archive hashes are recorded in `artifacts/hologram-transfer-validation-summary.json`, generated by `artifacts/summarize-hologram-transfer.ps1`, and in the timestamped root walkthrough.

## Limits

This validates built-in renderer/server behavior with embedded native player connections. It does not certify physical-client rendering, interpolation/input, arbitrary third-party renderer/transfer contracts, the complete installed modpack or actual proxy arrival. Ordinary custom renderer entities retain their existing same-world path; cross-dimension movement requires an owned NPC lifecycle. No production installation or original save data is modified. The broader Citizens command, data and integration checklist remains active.
